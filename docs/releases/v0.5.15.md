# codex-peer v0.5.15

This release lets Codex sessions and Codex lanes send and receive files through the `sessionbus` tool. Transfers need Sessionbus v0.5.14 or newer (daemon, and hub for transfers between hosts). With an older daemon they are refused and every other action stays available. Native Codex is installed separately and is not pinned.

`scripts/install-codex.sh` installs the latest published stable release by default, so it installs v0.5.15 once v0.5.15 is published as the latest stable release. Upgrading from v0.5.14 needs no lane-row change.

## Changes since v0.5.14

- **File transfer.** The `sessionbus` tool gains `transfer.offer`, `transfer.request`, `transfer.accept`, `transfer.status` and `transfer.cancel`, with the owner-approved wording from peer-common. The Sessionbus SDK performs the transfer:
  - files of up to 1 GiB are read and written as your OS user;
  - a received file is published only after its SHA-256 matches;
  - an existing destination is replaced only with `overwrite: true`.

  Offers, requests and each final result arrive as ordinary messages.
- **No permission layer of its own.** After a Sessionbus tool call is admitted, the SDK accesses files without applying the Codex thread sandbox and without asking for a native approval per path.
- **Paths are bound to the thread's working directory.** A relative `source` or `destination` is resolved against the Codex thread's working directory: for a lane, the directory native Codex confirmed when the lane opened. With no known working directory, only an absolute path is accepted. A `source` or `destination` key spelled any other way (for example `Source`) is refused; otherwise the SDK would read it without that binding.
- **Final results name the local file.** A transfer's final result gains this thread's local detail: the destination of a file it received, or a cleanup failure for a file it sent. To add it, the session can wait briefly for a publication in progress. A message arriving during that wait can be queued before the final result; every other message keeps its arrival order.
- **Refusals keep the caller connected.** With Sessionbus v0.5.14:
  - an offer to a session that cannot take transfers is refused with `unsupported_transfer` (-32018);
  - an operation that the transfer's ID, the caller's role or the transfer's state does not allow is refused with `transfer_failed` (-32019).

  Both are valid protocol errors, so the session and its lanes stay connected. The first was observed live.
- **Newer federation answers.** The newer SDK declares support for Sessionbus v0.5.14's federation additions, so these reach Codex sessions and lanes when the daemon and hub support them:
  - `list` can report a silent host as `not_responding`;
  - a hub policy refusal arrives as `federation_policy_denied` (-32017) instead of `unknown_session`.
- **Dependencies:**
  - the Sessionbus Go SDK is pinned at core commit `cd8aa6a9b7c385eecebb0639c065eb5ce55c41ba` (`v0.5.14-0.20261110081323-cd8aa6a9b7c3`), replacing `v0.5.9`. The SDK source does not change from that commit to the v0.5.14 release candidate `7f54c59`;
  - peer-common is pinned at `8c692a4694ac`, replacing `8348c6c8b18c`. Besides the transfer actions, it adds a private-request hook that codex-peer does not use.
- **Versions:**
  - `RELEASE_VERSION` is 0.5.15;
  - the Codex plugin source version (`codex/marketplace/codex/.codex-plugin/plugin.json`) is `0.5.15-codex.0`;
  - packaged archives carry `0.5.15-codex.g<revision>`, as before.
- No installer or workflow change in codex-peer.

## Evidence

Observed once each on one Linux host with native Codex 0.167.0. One operator ran them, and a reviewer read the results independently.

**With core `a831f180` and codex-peer `e752e48`** (2026-11-09):
- a 1 MiB file offered between two interactive sessions arrived with a matching SHA-256;
- a file requested from a lane arrived complete;
- an offer cancelled by its receiver ended `cancelled` on both sides, and no file was written;
- an accept without `overwrite` onto an existing file failed and left that file unchanged; a second offer accepted with `overwrite: true` replaced it;
- closing a lane during a 1 GiB transfer ended it `cancelled`, `endpoint_closing`, and left no temporary file;
- an offer to an older Claude peer dropped the caller's own connection and one of its lanes. That was a core defect, fixed in core `cd8aa6a9`.

**With core `cd8aa6a9` and codex-peer `28f58ec`** (2026-11-10):
- the same offer to an older Claude peer was refused with `unsupported_transfer`, and the caller and its lanes stayed connected;
- a lane with a 1-second auto-close, kept open by an accepted 1 GiB transfer, was still connected and streaming 49.7 seconds after its last run ended, and the file then arrived complete.

This release differs from `28f58ec` only in `RELEASE_VERSION`, the plugin source version, the two tests that expect them, and this file.

## Limits

- **One host only.** A transfer between two hosts through a hub was not run; it is planned after the release.
- **Federation additions not exercised.** `not_responding` and `federation_policy_denied` were not observed with a Codex session.
- **Not run against an older daemon.** That transfers are refused there and every other action still works was not checked live.
- **A notice waited for the lane's run to end.** In the lane check, the offer notice was not delivered into the lane's active run. It started a new run after that run ended.
- **Tool-only runs end `unavailable`.** A run started by a notice whose only work was a tool call ended `unavailable` ("no final answer"), and the transfer itself still completed.
- **Linux only.** Nothing in this release was exercised live on macOS.
- **Native is not pinned.** The checks used native Codex 0.167.0.
- **The limits of v0.5.14 stand.**
